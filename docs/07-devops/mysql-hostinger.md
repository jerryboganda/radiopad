# Database on Hostinger MySQL (API stays on the VPS) — runbook

**Status (2026-11-22): code written, nothing cut over.** Production still runs SQLite (`/data/radiopad.db`) with in-memory Hangfire.
All C# for this was written without a compiler (no `dotnet` on the dev machine) — **CI is the first real build.** Nothing in this
runbook has been executed against Hostinger. Do not start the cutover until the three gates below pass.

## Target topology

| Piece | Where |
| --- | --- |
| Marketing + admin web app (static) | Hostinger web hosting (unchanged) |
| API + `/ws` relay | VPS `185.252.233.186`, container `radiopad-api` (unchanged) |
| **Database** | **Hostinger MariaDB (remote)** — `RADIOPAD_DB_PROVIDER=mysql` |
| Hangfire jobs | the same MariaDB (`hangfire_*` tables) — queued push/email/webhooks survive restarts |
| Dictation audio | files on the VPS volume (`/data/uploads`, set `RADIOPAD_UPLOADS_DIR` if needed) — **not** in the database |
| Desktop sidecar | stays SQLite (the default); the switch is opt-in via env |

Hostinger shared hosting cannot run .NET, Docker or WebSockets, which is why only the database moves.

## Go / no-go gates — all three must hold

1. **TLS with certificate verification works** from the VPS to Hostinger (step 2). The database holds patient data (patient names and
   IDs are stored in plaintext) and will cross the public internet. In Production the API **refuses to start** with a MySQL connection
   string that does not set `SslMode=Required`, `VerifyCA` or `VerifyFull` (override `RADIOPAD_DB_ALLOW_INSECURE=1` exists and is unsafe).
   Prefer `VerifyFull` + a CA file; `Required` encrypts but does not authenticate the server.
2. **Round-trip latency is low** (step 2, target ≤ 20 ms per query). Every authenticated request makes roughly 5–9 sequential
   queries, so 30 ms RTT costs 0.15–0.3 s per call.
3. **You accept patient data on shared hosting.** I found no BAA/DPA statement for Hostinger shared MySQL, no documented TLS guarantee,
   and no SLA. A Hostinger outage becomes a total API outage (the compose healthcheck hits `/api/health`, which does not touch the DB;
   `/api/health/ready` does).

Limits to design around (Hostinger Unlimited/Business plan, from their docs — re-check in hPanel): 75 connections per database user,
3 GB database size, 120 s max query time. The API caps its connection pool at 20 (EF and Hangfire share the string); change it with
`Maximum Pool Size=` in the connection string only if you also lower the Hangfire worker count.

## Step 1 — create the database (hPanel, you)

1. hPanel → Databases → create a database + user with a long random password.
2. Databases → **Remote MySQL**: add the VPS IP `185.252.233.186` only. **Never "Any Host" / `%`.** Note the remote host name hPanel shows.
3. If hPanel offers a CA certificate for the MySQL host, download it to `/opt/docker/radiopad/data/hostinger-ca.pem` on the VPS.

## Step 2 — test TLS and latency from the VPS (read-only, throwaway container)

Nothing is installed on the shared VPS; the container is removed afterwards. Replace `<DB_HOST>`, `<DB_USER>`, `<DB_NAME>`.

```sh
# TLS + server facts (asks for the password)
docker run --rm -it -v /opt/docker/radiopad/data:/data:ro mariadb:10.11 \
  mysql --host=<DB_HOST> --port=3306 --user=<DB_USER> -p --ssl --ssl-ca=/data/hostinger-ca.pem --ssl-verify-server-cert <DB_NAME> \
  -e "STATUS; SELECT @@version, @@innodb_default_row_format, @@character_set_server, @@collation_server, @@max_user_connections;"
# If there is no CA file, a plain encrypted-but-unverified probe shows whether TLS is offered at all:
docker run --rm -it mariadb:10.11 mysql --host=<DB_HOST> --user=<DB_USER> -p --ssl <DB_NAME> -e "SHOW STATUS LIKE 'Ssl_cipher';"

# Latency: 50 statements over one connection; divide the elapsed time by 50
docker run --rm -it mariadb:10.11 sh -c 'time (printf "SELECT 1;%.0s" $(seq 50) | mysql --host=<DB_HOST> --user=<DB_USER> -p --ssl <DB_NAME> >/dev/null)'
```

Fail the gate if `Ssl_cipher` is empty, the verified connection fails, or the per-query time is well above 20 ms.
Also note `innodb_default_row_format`: it should be `dynamic` (a `compact` server can reject the wide `Report` table and the long index keys).

## Step 3 — generate the MySQL migrations (CI)

The existing 58 SQLite migrations cannot run on MySQL (they declare `TEXT` primary keys), and there is no `dotnet` locally, so the MySQL
history is generated by GitHub Actions from the model, into `backend/RadioPad.Api/src/RadioPad.Infrastructure/Migrations/MySql/`.

1. Actions → **mysql-migrations** → *Run workflow* (name `InitialMySql`). Before this workflow file is on `main`, push any commit to a branch
   named `mysql-migrations-request` and it runs the same job.
2. The job generates the migration, rebuilds, applies it to a blank MariaDB 10.11 with the `Category=MySql` tests, and only if green pushes
   branch `bot/mysql-migrations-<run id>` and uploads the files as an artifact.
3. Open a PR from that branch, read the generated SQL types (`char(36)` ids, `datetime(6)`, `longtext`, `utf8mb4`), and let **ci-mysql** pass.

`ci-mysql` (MariaDB service container) is the first thing that can fail: expect 1–3 iterations on Pomelo/Hangfire.MySqlStorage details I could
not check without a compiler. Its second step runs the entire existing integration suite on MariaDB as **informational** — treat the failures
there as a to-do list of SQLite assumptions, not as blockers for the cutover itself.

Every later schema change needs **two** migrations: one for SQLite/Postgres (`--context RadioPadDbContext`) and one from this workflow.

> **Merging to `main` deploys.** `web-deploy-images.yml` builds and deploys the API image on backend changes, so merging ships all the
> uncommitted audit fixes and the MySQL code together. Behaviour is unchanged until you set `RADIOPAD_DB_PROVIDER=mysql`
> (default stays SQLite). That deploy is the point where the new image exists on the VPS for steps 4–6.

## Step 4 — cutover (VPS, you; plan a maintenance window)

Compose lives in `/opt/docker/radiopad`. Never touch the other projects' containers.

```sh
cd /opt/docker/radiopad
docker compose stop radiopad-api
# 4a  cold backup — the SQLite file is the rollback
mkdir -p backups && cp -p data/radiopad.db* backups/ && ls -la backups
cp -p data/radiopad.db data/radiopad.db.copy        # the copier reads this file read-only
```

**4b  create the schema.** Start the new image once against the MySQL database so it migrates itself, then stop it. (No tenants exist yet,
so the boot-time seeding inserts no rows; the copier requires every table to be empty.)

```sh
docker run --rm --name radiopad-migrate --env-file .secrets.env \
  -e ASPNETCORE_ENVIRONMENT=Production -e RADIOPAD_BIND=http://0.0.0.0:7499 \
  -e RADIOPAD_DB_PROVIDER=mysql \
  -e 'ConnectionStrings__RadioPad=Server=<DB_HOST>;Port=3306;Database=<DB_NAME>;User ID=<DB_USER>;Password=<PASSWORD>;SslMode=VerifyFull;SslCa=/data/hostinger-ca.pem' \
  -v /opt/docker/radiopad/data:/data:ro radiopad-api:latest
# wait for "Application started", then Ctrl-C
```

**4c  dry run, then the real copy.** Copy mode runs instead of the web host and exits 0 (all row counts match) or 1. It prints table names and
counts only, never row values. Use the **same** `RADIOPAD_COLUMN_KEY_REF` / `RADIOPAD_COLUMN_KEY_WRAPPED` / `RADIOPAD_COLUMN_KEK` values the
running API uses (`.secrets.env` and the compose `environment:` block) — they are needed to decrypt and re-encrypt the secret columns.

```sh
COPY_ENV="--env-file .secrets.env -e ASPNETCORE_ENVIRONMENT=Production -e RADIOPAD_DB_PROVIDER=mysql \
  -e RADIOPAD_COLUMN_KEY_REF=<same as compose> -e RADIOPAD_COLUMN_KEY_WRAPPED=<same as compose> \
  -e RADIOPAD_COPY_FROM_SQLITE=/data/radiopad.db.copy \
  -e ConnectionStrings__RadioPad=<same MySQL string as 4b>"

docker run --rm $COPY_ENV -e RADIOPAD_COPY_DRY_RUN=1 -v /opt/docker/radiopad/data:/data:ro radiopad-api:latest   # counts only
docker run --rm $COPY_ENV                            -v /opt/docker/radiopad/data:/data:ro radiopad-api:latest   # copies
```

It refuses if the target has unapplied migrations, a missing table, or any non-empty table (fix: re-run 4b on a blank database; drop and
recreate the database in hPanel if a previous attempt left rows). Known failure: `MySQL error 1406` = a SQLite value longer than the column
(indexed strings are capped at 190 characters, `ExternalIdentity.Issuer`/`Subject` at 255) — it names the table, not the row.
Only `env:` and `local:` column-key stores work in copy mode.

**4d  switch the API.** Edit the live `docker-compose.yml` (hand-maintained; it differs from the repo copy): set

```yaml
      RADIOPAD_DB_PROVIDER: mysql
      ConnectionStrings__RadioPad: <the MySQL string with SslMode=VerifyFull>   # keep secrets in .secrets.env (deploy-owned, 600)
      RADIOPAD_UPLOADS_DIR: /data/uploads
```

then `docker compose up -d radiopad-api`. Check `https://api.radiopadstudio.com/api/health/ready` (touches the DB), sign in, open Audit → Verify.
Timestamps lose their last digit (SQLite keeps 100 ns ticks, MySQL microseconds): the audit chain hash does not use them, but its verification
orders by `CreatedAt`, so **run the audit verification now** and again after a few reports are signed.

**4e  update the repo copy** of `deploy/vps/docker-compose.yml` and `deploy/vps/README.md` to match (do it with `[skip ci]`; pushes under
`deploy/vps/**` otherwise trigger a production deploy).

## Rollback

Set the compose `ConnectionStrings__RadioPad` back to `Data Source=/data/radiopad.db`, remove `RADIOPAD_DB_PROVIDER`, `docker compose up -d`.
The SQLite file and `backups/` copy are untouched. **Writes made while on MySQL are not copied back.**

## After cutover

* **Backups move to MySQL.** The old runbook ("stop the container and copy `radiopad.db`") no longer covers production data. Schedule a nightly
  encrypted `mysqldump --single-transaction` from a throwaway `mariadb:10.11` container to `/opt/docker/radiopad/backups/`, and check what
  Hostinger backs up on its side (unknown). Keep a restore drill on the calendar.
* Delete the SQLite copies (`radiopad.db*`, `radiopad.db.copy`, `backups/radiopad.db*`) once you trust the new database — they are patient data.
* `RADIOPAD_UBAG_ALLOWED_TARGETS` in the live compose still lists `mock`; remove it unless you want the mock UBAG target selectable.

## What is verified, what is not

* Verified by reading: provider selection (`DbProviderSelector`), the TLS/pool guard, the copier's refusal rules, the workflows' YAML parses.
* **Not verified (no compiler, no Hostinger access):** that any of the C# compiles; Pomelo 8.0.2 type mappings; `Hangfire.MySqlStorage` 2.0.3
  (unmaintained since 2020) with Hangfire 1.8.24 and MariaDB; `dotnet ef --startup-project` with this minimal-hosting `Program.cs`;
  Hostinger's TLS, row format, MariaDB version, latency, connection throttling.
* Code map: `Persistence/DbProviderSelector.cs`, `MySqlRadioPadDbContext.cs`, `SqliteToMySqlCopier.cs`, `RadioPadDbContext.ConfigureMySql`,
  `Jobs/HangfireSetup.cs`, tests in `tests/RadioPad.Api.Tests/MariaDb/`, workflows `mysql-migrations.yml` and `ci-mysql.yml`.

## Measured gate results (2026-11-23, from the VPS)

* **Gate 1 (TLS): passes.** `srv1864.hstgr.io` (153.92.15.53:3306) offers TLS 1.3 (`TLS_AES_256_GCM_SHA384`) with a valid Let's Encrypt
  certificate for `*.hstgr.io`; `openssl s_client -starttls mysql` verifies OK. Use `SslMode=VerifyFull` with the system CA store.
* **Gate 2 (latency): FAILS.** TCP connect from the VPS to the Hostinger MySQL host takes **170-290 ms** (5 samples), against a target of
  <= 20 ms. A fresh TLS connection costs ~0.7-0.8 s. At 5-9 sequential queries per authenticated request that adds roughly 1-1.5 s to every API
  call (and more for login). **Do not cut over** while the API runs on this VPS; either keep SQLite on the VPS volume or run MariaDB next to the
  API (same host). Revisit only if the API moves to a host with low RTT to Hostinger.
* hPanel state left in place: database `u372263031_radiopad`, user `u372263031_rpapi`, Remote MySQL rule for `185.252.233.186`
  (`RADIOPAD_MYSQL_PASSWORD` is stored in the VPS `.secrets.env`). The first authenticated probe returned error 1045 (password mismatch), so
  credentials were never validated. Delete the rule, user and database if this path is abandoned.
